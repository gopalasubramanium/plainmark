# Code signing policy

The **v0.4.0 Mac apps and DMGs are Developer ID-signed, Apple-notarized, and verified by Gatekeeper** for Apple Silicon and Intel. The public baseline remains an early release; its direct Windows installer remains unsigned. The historical v0.3.3 Mac downloads remain signed and notarized. The older published v0.2.2 preview still has ad-hoc Mac signatures and an unsigned Windows installer. Build provenance and checksums serve a different purpose from OS publisher signatures; describe the status of the exact downloaded asset.

## macOS

The [verified macOS signing run](https://github.com/gopalasubramanium/plainmark/actions/runs/34731391796) signs both Apple Silicon and Intel packages, requires real credentials, checks Developer ID and the expected team, verifies the hardened runtime, and validates stapled notarization tickets and Gatekeeper assessments for **both the app and its outer DMG**. App notarization alone is not enough to establish the DMG's download trust. Fresh downloads passed those checks locally, and apps inside read-only mounted DMGs matched the corresponding archives. The signed Apple Silicon app passed native Open, visible rendering, source editing and exact saved-content verification. The source tag is `v0.4.0`, commit `67a98521c49d1c77605a43b21eacfe17e285ed54`. A physical Intel Mac installation has not been tested. The workflow leaves the release as a draft and fails rather than silently producing an ad-hoc build.

The publisher needs an active [Apple Developer account](https://developer.apple.com/account/) and a valid Developer ID Application identity. The original signing key is retained in the local login Keychain; an encrypted certificate/key export and notarization credentials are stored in GitHub environment secrets. No private key export or plaintext credential file is committed to the project.

Use a **Developer ID Application** certificate for distribution outside the Mac App Store. Add the following through GitHub's encrypted `release-signing` environment secrets, never source files or chat: `APPLE_CERTIFICATE` (exported P12 encoded as base64), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `APPLE_ID`, `APPLE_PASSWORD` (an Apple **app-specific** password, not the account password), and `APPLE_TEAM_ID`. The environment permits workflow runs from `main` only, requires the maintainer's approval before credentials are available, and disables administrator bypass. The workflow separately validates the requested unpublished version tag and serializes signing with ordinary builds of the same tag. Certificates and account authorization must belong to the responsible publisher.

First complete the ordinary all-platform release checks for a new, unpublished version tag. Then dispatch the signed workflow with that exact tag. Verify both architectures and fresh-download installation before publishing the draft. Never silently replace binaries in an already public release: use a new version. [Apple Developer ID](https://developer.apple.com/developer-id/) and [Tauri's signing and notarization guidance](https://v2.tauri.app/distribute/sign/macos/) describe the platform requirements.

## Signing roles and privacy

Gopala Subramanium ([gopalasubramanium](https://github.com/gopalasubramanium)) is the maintainer, author, reviewer and release approver. Changes from outside contributors require maintainer review. Production signing requires maintainer approval; automated checks do not grant signing approval. SignPath onboarding must verify MFA on repository and signing accounts before production use.

Plainmark does not transfer document contents to networked systems. External links open only when requested; installation may download Microsoft WebView2 if it is missing. See the [privacy policy](../PRIVACY.md) for local recovery storage, optional actions and system components.

## Windows

**[Microsoft Store is available](https://apps.microsoft.com/detail/9pb6h8z02k0g)**, with the public listing verified on 13 September 2026. Microsoft handles signing of Store-distributed MSIX packages. This listing check did not independently inspect the signature or install the Store-delivered package; the tested submission candidate and coverage limits are recorded in [Windows packaging](../packaging/windows/README.md).

The primary Windows download now uses [Microsoft’s official web installer](https://get.microsoft.com/installer/download/9PB6H8Z02K0G). It is a small online installer that retrieves the Store edition. Microsoft handles Store MSIX package signing and Store-managed updates; it does not sign the separate GitHub EXE. Installation requires internet access, Store service availability, a supported Windows device and permission under the device’s policies. Keep the [Store listing](https://apps.microsoft.com/detail/9pb6h8z02k0g) as a fallback route, and do not present the web installer as a fully offline or Store-independent package. [Microsoft Web Installer documentation](https://learn.microsoft.com/en-us/windows/apps/distribute-through-store/how-to-use-store-web-installer-for-distribution) · [Microsoft signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options).

On 16 September, the exact official endpoint returned HTTP 200, a Windows executable named `Plainmark Markdown Editor Installer.exe`, 815,136 bytes, SHA-256 `46fe7ab0787574eaab2b184fb264801dcc5ecf2fc4001192035daef4b3a9813e`. Its certificate table includes Microsoft Corporation certificates. This confirms the download and certificate presence, not Windows Authenticode trust or successful installation; those checks remain outstanding. Microsoft generates and services this installer, so this observed hash is an audit record, not a permanent pin for the download URL. Link to Microsoft’s current endpoint instead of copying or renaming this file as an immutable Plainmark release artifact.

The separate direct EXE download remains unsigned. A [SignPath Foundation](https://signpath.org/) application was submitted on 12 September and declined on 16 September 2026 because Plainmark does not yet have sufficient external adoption and visibility. The provider invited reapplication after broader recognition; it did not identify an app quality or security defect. No direct-download signing certificate has been issued. The Foundation supports eligible open-source projects without charging the project for signing. Approval, policy compliance, artifact configuration and access setup are required; free service is not automatic. See [the application record](SIGNPATH-APPLICATION-DRAFT.md) for onboarding status. Sponsorship and signing are not active until the provider approves and verifies the project.

If a future application is approved, configure the official SignPath integration so it signs the application executable inside the installer and the outer NSIS installer, preserving the artifact structure and provenance. Authorize production signing only for reviewed version tags and require the maintainer to approve signing requests. Download the returned signed artifact, verify its contents, then run `scripts/verify-windows-signature.ps1` with the actual approved publisher subject. Pass both `-Installer` and `-Application` (the actual installed or extracted app), plus `-Uninstaller` for NSIS packages. The verifier requires distinct files, valid timestamped Authenticode signatures and the same approved publisher certificate for every file. Signing only the outer installer is insufficient. Windows CI exercises rejection of unsigned/tampered files, wrong publishers, missing timestamps and mismatched inner signatures. The provider configuration cannot be completed until SignPath supplies the project/artifact/policy identifiers. Do not claim Foundation sponsorship or add its required sponsorship credit before acceptance.

An alternative is an eligible certificate authority or [Microsoft Artifact Signing](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart). Microsoft's current public-trust eligibility includes Singapore organizations but individual developers only in the United States and Canada. Choose the correct legal identity; do not create an organization or misstate a country to bypass eligibility. Any paid service requires a separate cost decision.

A valid signature identifies the publisher and detects tampering. It does not guarantee that every new binary passes SmartScreen without a warning; Microsoft explicitly distinguishes signing from reputation and enterprise policy. EV certificates no longer provide an immediate universal bypass. The available Microsoft Store edition uses a separate distribution and signing route from the direct EXE. [Microsoft's current explanation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation).

## Linux and reproducible provenance

There is no one Linux-wide equivalent of Apple's notarization approval. Publish Debian and AppImage checksums and GitHub artifact attestations linking the exact installers to their source/workflow. Release jobs prepare these after building. Consumers can verify an artifact with `gh attestation verify <downloaded-file> --repo gopalasubramanium/plainmark`, and compare its SHA-256 against the corresponding release checksum file. A checksum downloaded from the same compromised origin would not independently establish authenticity.

The Debian desktop entry, MIME registration and actual packaged launch command are checked in Linux CI. Future distribution through a maintained package repository or Flathub would add platform-specific review and signing, with separate packaging work. Source availability alone does not establish bit-for-bit reproducibility across machines; that property has not been proven.

## Release decision

A release is ready to be described as trusted only when its platform-specific checks succeed and actual installation has been verified on that platform. Document signature status per asset. OS defaults remain the user's choice through Open with / default-app settings. A signature cannot force adoption, bypass organizational restrictions or guarantee a warning-free installation on every machine.
